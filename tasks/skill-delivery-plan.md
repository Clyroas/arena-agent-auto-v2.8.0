# Implementation Plan: Full Skill Delivery

Status: **approved implementation plan; execute one task at a time with verification gates**.
Requirements: [CAPABILITY-MAP.md](../CAPABILITY-MAP.md) and `SPEC-skill-catalog.md`, `SPEC-skill-selection.md`, `SPEC-skill-inline-delivery.md`, `SPEC-skill-attachment-overflow.md` at the repository root. Tasks/checkpoints: [skill-delivery-todo.md](skill-delivery-todo.md). The unrelated unfinished `tasks/plan.md` and `tasks/todo.md` are preserved. Do **not** use `/build`'s default task target for this initiative; explicitly use this plan and checklist.

## Overview

Let a person using the Arena Auto Chat panel review and explicitly choose one full skill per task, then send its complete primary `SKILL.md` inline when it fits or attach a transient `.md` with explicit consent when it does not. Build from 25 MIT-pinned engineering skills, the 14 individually licensed Apache-2.0 Anthropic public examples at commit `33375500bcea98d610eb30ce10ac4e59b89c390d`, and four *original* Arena-appropriate document-format alternatives. No automatic selection, runtime fetch, unlicensed/restricted content, external references, scripts or assets.

## Approved architecture

1. **Sources and release data are separate.** Keep the current `.agents/` vendor unmodified. Pin the 14 upstream primary texts with a license/source manifest in a development-only source area and author four original `SKILL.md` files separately. A dev-only deterministic Node generator produces a static catalog ES module checked into Git and allow-listed in `extension-files.json`. No runtime build/network/dependency; package no raw source directories. Include Apache/MIT notices and provenance in the shipped catalog/notice artifact. Tests compare generated bytes to sources and verify a reviewed allow-list. A source refresh requires an explicit audit and regeneration.
2. **Selection is panel-local, not a page-side capability.** Add search/source/compatibility labels, a scrollable unmodified-text viewer, a single active skill ID, and change/remove controls to the shared `panel.js` UI and mirrored panel/floating markup. No persistent selection or task data. Preserve the existing short Task prompts picker and its behavior. Selection alone never calls the adapter.
3. **Compose at Send.** Keep task and selected skill as separate in-memory values until the explicit Send action. A pure helper deterministically wraps the exact `SKILL.md` plus task and an attributed compatibility caveat; it either fits the 30,000-character budget **without truncation** or reports overflow. The normal direct-port Send path remains one attempt. Clear selection only after verified acceptance; preserve draft/selection on safe pre-click failure. No change to wire protocol anticipated; if it proves necessary, follow the version-sync rule before implementation.
4. **Overflow is a consented file in the same turn.** On overflow, require a separate confirmation at Send and create a transient `.md` File from the exact skill text. Confirm remaining four-file capacity and actual page file-input compatibility before staging, then reuse existing attachment ownership, one-shot stage grant and single Send. Never evict user files, silently change task text, split into multiple messages, or retry an ambiguous send. No claim the agent read an uploaded file without live evidence.

These are proposals for implementation, not permission to change the approved module scope. Any new privilege, different source, multi-skill selection or forced fallback returns to spec review.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Restrictive or missing licenses (`docx`, `pdf`, `pptx`, `xlsx`, `doc-coauthoring`) | High | Explicit exclusion test; four independently written alternatives; source/license provenance at pinned commit; no source import without audit. |
| Skills reference unavailable Claude tools/paths or references that are not packaged | High | Preserve exact primary text, show a separate prominent compatibility warning; no promise of tool access; test original alternatives for Arena-appropriate wording. |
| Full skill text exceeds 30,000 chars (`claude-api` alone ~86 KB) | High | Compose without truncation; confirmed `.md` fallback; fail closed on page upload incompatibility, four-file cap or >8 MiB; don't send a task without its skill. |
| Arena accepts an upload but the agent cannot read it | High | Synthetic upload test + manual live Arena readback before ship; if unverified, mark overflow incomplete and do not claim full-feature readiness. No automatic retry after uncertainty. |
| New generated files or UI break extension package/parity | Medium | Deterministic generator + packaging tests; panel/floating parity tests; version-sync test if adapter changes. |
| Accidental privacy or send-regression | High | Keep selected skill/task in panel memory; use existing one-shot send; test cancelled/pre-click/ambiguous paths and no-skill behavior; no new permissions/network/storage. |
| Existing unrelated plan gets lost | Medium | Use `tasks/skill-delivery-*.md`, do not modify `tasks/plan.md`/`tasks/todo.md` (user-approved storage decision). |

## Verification strategy

For each slice: write a failing focused test first, implement the minimum, run its focused `node --test test/<name>.test.mjs`, then `npm run check` before marking complete. Catalog package audit: `npm run package:extension`. UI/transport synthetic browser fixtures: `npm run test:browser` if Chromium is available. Before shipping, manually verify on an authorized live Arena Agent tab that inline text is delivered once, an overflowing `.md` is readable by the agent, and unsupported input/failed staging sends nothing. If live validation cannot be performed, report the gap and stop short of a shipping claim.

## Decisions confirmed at plan review

1. Use a **single checked-in generated ES module + development-only pinned source data**, not raw `.agents/` directories in the release artifact.
2. Prefer the existing attachment transport with a user-confirmed generated `.md` File in the panel. If evidence forces a wire-contract change, return for review and synchronized version bump.
3. The catalog/UI/send checkpoints and task sizing are approved. Proceed one task at a time; each checkpoint and any scope change remains a review gate.
